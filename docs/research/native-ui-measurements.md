# Замеры нативного интерфейса (без WebView2)

Журнал замеров к `docs/native-ui-roadmap.md`: каждый этап переноса дописывает сюда свои числа.

## Этап 0a — ядро окон `src-tauri/src/native/` (2026-11-01)

**Что мерилось.** `cargo run --release --example native_demo`: одно прозрачное окно поверх всех
380×600 DIP, внутри — кадры маскота `frontend/mascot/idle_*.webp` (96 кадров 384×512, рисуются в
180×240 DIP, 24 кадра спрайта в секунду), 7 строк текста (Geologica, Handjet с осями ELSH/ELGR,
Martian Mono, арабский с переносом справа налево, японский, корейский, китайский через системный
подбор шрифтов) и две заливки. Окно анимируется непрерывно — это худший случай для маскота
(у веб-маскота анимации тоже идут всё время, пока он на экране).

**Машина.** Windows 11 Enterprise 10.0.26300, 16 логических ядер, два монитора по 96 DPI
(основной 2560×1440 с частотой 180 Гц). Сборка `release` (LTO). Во время замеров рядом шли сборки
cargo другого агента, поэтому CPU плавает — ниже указан разброс между прогонами.

**Как читать CPU.** «% ядра» — доля одного логического ядра (100 % = ядро занято целиком),
в скобках — доля всего процессора, как в диспетчере задач. Окно замера — 10 с, после прогрева.

### CPU

| Режим | Кадров/с | CPU, % ядра | CPU, % всего ЦП |
|---|---:|---:|---:|
| Покой: окно на экране, анимации нет (`--static`) | 0 | **0,00** | 0,00 |
| Лимит 30, установившийся (кадры спрайта в кэше, `--warmup 5`) | 30,0 | **0,31** | 0,02 |
| Лимит 60, установившийся | 58,5–60,0 | **0,9–2,3** | 0,06–0,15 |
| Без лимита (как монитор, 180 Гц), установившийся | 179,9 | **7,3** | 0,46 |
| Лимит 30, первый круг анимации (каждый кадр спрайта декодируется WIC) | 30,0 | 7,3–7,8 | 0,45–0,49 |

- Перерисовка только по необходимости работает: окно без анимации не тратит CPU вовсе —
  поток окон спит в `MsgWaitForMultipleObjectsEx` без таймера.
- Основная цена первого круга — декодирование WebP (≈3 мс на кадр 384×512 → 180×240).
  После первого круга кадры берутся из кэша; весь цикл `idle` при 100 % занимает 15,8 МБ.
- Текст почти ничего не стоит: прогон без текста (`--no-text`) и с ним дают одинаковый CPU,
  глифы Direct2D кэширует сам.

### Память (процесс демо, рабочий набор / частные байты)

| Состояние | Рабочий набор | Частные |
|---|---:|---:|
| Процесс до создания окон (поток окон уже запущен) | 10,3 МБ | — |
| Пустое окно: устройство D3D11/D2D/DComp, без текста и спрайта | 45–51 МБ | 56–57 МБ |
| Окно с текстом, анимация стоит (1 кадр спрайта в кэше) | 54,7 МБ | 58,5 МБ |
| Окно с текстом и анимацией, все 96 кадров в кэше | 56,4–57,0 МБ | 78–80 МБ |

- Около 35–40 МБ рабочего набора — сам графический стек (пользовательская часть драйвера
  видеокарты, D3D11, Direct2D, DirectComposition, DirectWrite). Эта цена платится один раз на
  процесс, а не на окно.
- Кэш кадров добавляет ~20 МБ частных байт при 15,8 МБ пикселей — копии под текущий масштаб,
  а не 384×512 (полноразмерные 296 кадров маскота заняли бы 230 МБ).

### Время до первого кадра

| Сценарий | Время |
|---|---:|
| Запуск потока окон (`UiThread::spawn`: COM, DirectWrite + 3 встроенных шрифта, WIC) | 8–9 мс |
| Предпрогрев `Ui::prewarm` (устройство D3D11 + D2D + DComp, кодеки WebP/PNG) | 260–330 мс (один выброс 504 мс) |
| Первый кадр окна после предпрогрева: окно, swap chain, 7 разметок текста, 1 кадр WebP | **33–37 мс** |
| То же, окно без текста и спрайта | 14–16 мс |
| Первый кадр без предпрогрева (`--cold`, устройство создаётся в первом кадре) | 347–404 мс |

Вывод для этапа 1: `prewarm` звать при старте программы (в потоке окон, фоном), тогда маскот
появляется через ~35 мс после запроса, а не через 0,3–1 с, как веб-окно.

### Проверки, не числа

- Прозрачность попиксельная: скругления подложки и силуэт маскота смешиваются с рабочим столом.
- Арабский — справа налево, перенос по словам; иероглифы и хангыль — без квадратиков.
- Масштаб: окну прислан `WM_DPICHANGED` 144 (`--fake-dpi 144`) — окно стало 570×900 px,
  текст и кадры чёткие, кадры перекэшированы под новый пиксельный размер.
- Потеря устройства (`--device-loss`): устройство, swap chain, цель DirectComposition и кэш
  пересоздаются, окно рисуется дальше без видимого сбоя.

### Для сравнения: текущий веб-маскот

- WebView2 держит **~180 МБ**, пока жив хотя бы один веб-вид (в трее — окно маскота); это
  несколько процессов (browser, GPU, renderer, utility), см. `docs/research/ui-memory.md`.
- Окно WebView2 появляется через 0,3–1 с (запуск веб-движка).
- Нативное ядро: **~57 МБ рабочего набора на весь процесс-демо** с анимированным окном, из них
  ~10 МБ — сам процесс без окон; появление окна ~35 мс после предпрогрева.

Это замер демо, а не маскота: настоящий маскот (этап 1) добавит свечение (размытие эффектом
Direct2D), жидкость в глазу и 296 кадров вместо 96 — его замер против веб-версии и есть ворота
этапа 1.

## Этап 1 — нативный маскот (`native_mascot`) против веб-маскота (2026-11-01)

**Как мерилось.** Сборка с оптимизацией (`--release`, thin LTO) и `debug_assertions`, чтобы
настройки читались из `src-tauri/resources/settings.json`, а не из настроек установленного
Reever. Режим `REEVER_MASCOT_DEMO=1` (без микрофона и горячих клавиш, `mascot_demo.rs`), запуск
`--hidden` — главное окно не создаётся, как при свёрнутом в трей. Маскот в режиме `always`,
размер 100 %, «Плавность» — как у монитора (180 Гц), локальный индекс выключен (иначе на старте
обход дисков забивает CPU). WebView2 запускался со своей папкой данных
(`WEBVIEW2_USER_DATA_FOLDER`): без неё тестовый процесс подключается к браузерному процессу
установленного Reever и его WebView2 не отделить. Считается рабочий набор / частные байты
reever.exe и всего дерева его процессов msedgewebview2. По два прогона каждого варианта; CPU —
доля одного ядра за 3 с, пока маскот стоит на экране (покой, анимация idle и свечение).

| Вариант | reever.exe WS / private | WebView2 (процессов, WS / private) | Всего WS / private | CPU, % ядра |
|---|---:|---:|---:|---:|
| Веб-маскот, пузырь выкл. | 42 / 10–12 МБ | 6–7, 374–383 / 298–301 МБ | **416–425 / 309–311 МБ** | 15,6 |
| **Нативный маскот, пузырь выкл.** | 73–74 / 121–123 МБ | **0** | **73–74 / 121–123 МБ** | **7,2–9,1** |
| Веб-маскот, пузырь вкл. (по умолчанию) | 43 / 11–12 МБ | 7–8, 438–451 / 335–340 МБ | 481–493 / 347–353 МБ | 17,5–17,9 |
| Нативный маскот, пузырь вкл. | 83–85 / 124 МБ | 7, 315 / 159 МБ | 398–400 / 283 МБ | 7,5–8,0 |

Выводы:
- **Без пузыря WebView2 исчезает совсем**: −350 МБ рабочего набора и −190 МБ частных байт на
  весь процесс, CPU вдвое ниже (рисование маскота и линзы — в процессе Reever на видеокарте,
  без отдельного GPU-процесса браузера).
- **Пузырь (`bubble.html`) пока веб** и один держит дерево WebView2 (browser, GPU, utility,
  renderer): ~315 МБ. Полный выигрыш с пузырём по умолчанию — только после этапа 2.
- Частные байты нативного варианта (~120 МБ) больше рабочего набора: это резервирования
  драйвера видеокарты и D3D11, а не данные маскота; кэш кадров маскота при 100 % — единицы МБ.
- Числа отличаются от «~180 МБ» в начале документа: здесь WebView2 со своей папкой данных и
  полным деревом процессов (browser + GPU + utility + renderer), как у Reever без второго экземпляра.

**Внешний вид** сравнивался снимками угла экрана в одних и тех же шагах сценария (idle, wake,
listening с уровнем голоса, heard, busy, paused, отказ wake, приход и уход через портал в режиме
`commands`, знакомство, переключение веб ↔ нативный на лету): кадры спрайта, положение, линза с
жидкостью, вспышка, тёмный глаз на паузе, портал с затягиванием и искры совпадают. Отличия —
в разделе «Нативный маскот: что отличается» ниже.

**Мышь** (SendInput на нативном окне): угол окна и место сбоку от силуэта пропускают клик в окно
под маскотом (WindowFromPoint — чужое окно); над головой окно ловит мышь, курсор — «рука»;
перетаскивание за голову сдвигает окно ровно на путь курсора (−300, −150).

**Масштаб:** `mascot_scale` 150 — окно 492×612 px, маскот стоит в углу рабочей области;
WM_DPICHANGED 144 (как перенос на монитор 150 %) — окно 492×612, кадры и линза перекэшированы
под новый пиксельный размер, чётко. Реальный монитор 150 % не проверен — у машины оба по 100 %.

### Нативный маскот: что отличается от веб-версии

- Свечение: эффект Gaussian blur Direct2D с тем же радиусом (σ = 10 и 3 базовых пикселя),
  посчитанный на полном размере; в вебе — `blur()` на холстах, уменьшенных в 4 и 2 раза. Ореол
  на снимках совпадает по ширине, точного попиксельного сравнения нет (разный фон под окном).
- Окно ловит мышь только над непрозрачными пикселями осьминога (альфа кадра, уменьшенная до
  96×128); веб-окно ловило её над всем прямоугольником 164×204 вокруг осьминога в покое.
- Курсор: «рука» над головой, «перемещение» в руке — у Windows нет курсоров grab/grabbing.
- Искры портала — те же числа, но случайные: картина каждый раз своя (как и в вебе).
