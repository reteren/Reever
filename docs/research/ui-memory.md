# Память и CPU интерфейса WebView2

Срез: 2026-10-16. `reever.exe` не запускал; код программы и конфиги не менял. Суммы из задания — исходный baseline; отдельно снят один read-only снимок памяти уже запущенных процессов через `Win32_Process`/`Get-Process`. Размеры файлов и картинок измерены на диске; размеры декодированных изображений, mipmap и canvas ниже — расчёт по фактическим размерам и RGBA8, а не замер диспетчера задач. CDP/JS heap и idle CPU не профилировались.

| Шрифты | Три TTF вместе — **781,012 bytes (0.745 MiB)** | Файлы измерены; resident-кэш шрифта/глифов отдельно не снимался. Это существенно меньше рамки и двух renderer-процессов. |

Microsoft описывает отдельные browser, GPU, utility и renderer процессы; обычно на каждый WebView control приходится свой renderer. Поэтому скрытый `picker` — реальная цена, а не только стоимость его 369 KB файла. [WebView2 process model FAQ](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/end-user-faq), [Performance best practices](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance).

## Сравнение вариантов

Значения в MB — baseline из задачи. Там, где абсолютное значение нельзя получить из пиксельной формулы, указано `оценка`; GPU/private-счётчики после изменения нужно снять повторно на том же окне и состоянии.

| Вариант | Открытое окно: память | В трее: память | Цена |
|---|---|---|---|
| Сейчас: скрыть окно, оставить WebView | около 475/660 MB | примерно те же 475/660 MB; `shell.js` останавливает rAF, но renderer, GPU и контексты остаются | Без задержки, исходное качество. |
| Уменьшить рамку до 1× | **Оценка:** не выше baseline; расчётно убрать до 60.16 MiB из пары decode/texture-буферов | То же уменьшение, но скрытие само по себе ничего не освобождает | На DPR 2 рамка может стать мягче; проверить 1×/2× и compact на реальном экране. |
| Сжать WebP сильнее, оставить 2× | около baseline; размер GPU/decoded texture не меняется | около baseline | Меньше файловый объём, но RAM почти без выигрыша; возможны артефакты цвета и нормалей. Исходники уже WebP. |
| При скрытии потерять WebGL-контексты и очистить canvas | Открыто: около baseline | **Оценка:** освободить до 45.83 MiB текстур и 4.3–17.2 MiB frame canvas backing; renderer и общий WebView2 набор остаются | Контексты, шейдеры, mipmap и текстуры нужно создать снова при показе; возможна пауза/вспышка первого кадра. Это альтернатива уничтожению окна, не дополнительный выигрыш поверх него. |
| `main` и `picker` создавать по требованию, уничтожать перед уходом в трей | **Оценка:** без `picker` около 401–448/504–595 MB private/working, если вычесть один из двух renderer из текущего baseline; после первого поиска вернётся к baseline, пока picker жив | **Оценка:** 0 процессов WebView2 Reever, если уничтожены оба окна; процесс Rust с tray/audio остаётся | Холодный показ дороже. В предыдущем замере Tauri 2 на Windows полное пересоздание окна заняло 295–303 ms (3 прогона; не замер Reever). После использования picker уничтожать, иначе он удержит WebView2 в трее. |
| `additional_browser_args`: cache / JS heap / process flags | Нет измеренного выигрыша; память почти наверняка останется около baseline | Нет выигрыша поверх lifecycle | `--disk-cache-size` меняет кэш на диске, не размеры WebGL/canvas. `--js-flags=--max-old-space-size=…` ограничивает V8 heap, но не GPU/native буферы и повышает риск OOM. Не форсировать `--single-process` и не отключать GPU: это не доказанный путь сокращения памяти и может сломать изоляцию/ускорение WebGL. |
| Ограничить idle-кадры | память практически та же | уже остановлено кодом скрытия | При 20 fps вместо 60 — расчётно на 67% меньше вызовов/отрисовок в idle, но это не обещает −67% CPU. Небольшая потеря плавности спокойной анимации; в listening/busy/при наведении оставить 60 fps. |

Для динамического создания Tauri 2.11.3 из lockfile имеет `WindowConfig.create: false`, `WebviewWindowBuilder::from_config`, а `additionalBrowserArgs` есть в конфигурации и в builder. У Tauri/Wry разные browser args требуют отдельные data directories; custom args также требуют сохранить нужные Wry default flags. Поэтому кэш/heap/process аргументы не рекомендую включать без A/B-замера. [Tauri WindowConfig](https://docs.rs/tauri-utils/2.9.3/tauri_utils/config/struct.WindowConfig.html), [Tauri WebviewWindowBuilder](https://docs.rs/tauri/2.11.3/tauri/webview/struct.WebviewWindowBuilder.html).

## CPU в покое

CPU-процент не снимался: чтение rAF-кода не заменяет профилирование. Сейчас видимое окно в `shell.js::loop` за каждый кадр обновляет spring-параметры, WebGL frame/core, Canvas2D частицы и эквалайзер; idle также оставляет 22 ember-частицы и периодический sweep. При 60 fps это 60 проходов и полных обновлений кадра в секунду; скрытый документ останавливается через `visibilitychange` и резервную проверку `isVisible` раз в секунду.

Рекомендация: активное listening/busy, ввод, наведение и короткий sweep — 60 fps; idle/paused — ограничить до **20 fps** через редкое расписание `setTimeout → requestAnimationFrame`, а после завершения пружин и частиц остановить JS-петлю до нового события или следующего sweep. Просто пропускать два из трёх rAF callback не снизит число callback-ов. Проверить CPU и задержку реакции в профиле после реализации; в idle можно отключить появление новых ember, если 20 fps заметно ухудшает вид.

## Рекомендация и этап 2

Первым делать lifecycle окон: по аналогичному Tauri замеру это должно убрать почти весь WebView2 набор в трее при сохранении исходного качества, тогда как 1× ограничивает выигрыш примерно 60 MiB суммарных texture/decode-буферов, а lossy на тех же размерах не освобождает их. Picker сделать ленивым и уничтожать при закрытии; сначала проверить холодную задержку поиска. Если по продукту окно нельзя уничтожать, резервный путь — явные `dispose()` в `frame.js`/`orb.js` (`WEBGL_lose_context`, очистка текстур и уменьшение Canvas2D) при hide и повторная инициализация при show.

Конкретные правки:

1. `src-tauri/tauri.conf.json`: выставить `create: false` для `main` и `picker`, сохранив остальные параметры текущих окон.
2. `src-tauri/src/lib.rs`: добавить создание `main` из `app.config().app.windows` через `WebviewWindowBuilder::from_config`; `show_main` должен создавать окно при отсутствии. При уходе в трей уничтожать `main`; перехватывать `RunEvent::ExitRequested` с `code == None`, чтобы процесс с tray/audio не завершался при отсутствии окон. Перенести обработчики `WindowEvent` в helper создания окна и сбрасывать одноразовый `WINDOW_SHOWN`: сейчас `window_ready` показывает только первое созданное окно. Строить окно из отдельного потока/async-пути: синхронный builder в Windows-команде или обработчике может зависнуть.
3. `src-tauri/src/picker.rs`: создавать `picker` только при первом `найди`, после выбора/закрытия уничтожать. После создания дождаться загрузки `picker.html` и затем послать `reever://picker`, иначе событие может уйти до подписки страницы.
4. `frontend/skin/shell.js`: направить `#shadeTray` в тот же Rust lifecycle путь (сейчас кнопка напрямую делает `win.hide()`); сделать idle scheduler 20 fps и активный 60 fps; будить анимацию событиями `reever://state`, `reever://level`, указателем и текстовыми изменениями, останавливая после затухания.
5. `frontend/skin/frame.js`, `orb.js`: при выбранном варианте без уничтожения окна добавить явные `dispose/recreate` API; не делать это одновременно с уничтожением WebView без замера.
6. `frontend/skin/frame_color.webp`, `frame_normal.webp`: отдельно подготовить 1× копию и сравнить на DPR 1/2; не менять размеры lossy-кодированием как «оптимизацию памяти».

Основание для tray lifecycle: в локальной памяти есть измерение Tauri 2.11.5/WebView2 149.0.4022.98: два скрытых окна удерживали 6–8 процессов, после уничтожения последнего окна процессов Reever WebView2 стало 0; cold open составил 295–303 ms. Это другой Tauri-проект, поэтому числа задержки и точной памяти — только ориентир, затем требуется замер Reever. `<vault>/KNOWLEDGE/tooling/tauri-2-на-windows-жизненный-цикл-окон-webview2.md`.
