# Parakeet TDT 0.6B v3: эксперимент с int4-энкодером

Эксперимент выполняется отдельно от Reever. Установленная int8-модель и код приложения не меняются.

## Исходная модель и воспроизведение

Указанный [архив k2-fsa с FP32-моделью](https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/sherpa-onnx-nemo-parakeet-tdt-0.6b-v3.tar.bz2) 2026-10-21 отвечал HTTP 404. Поэтому взят [совместимый с sherpa-onnx FP32-экспорт](https://huggingface.co/Yiivgeny/parakeet-tdt-0.6b-v3-sherpa-onnx-fp32). SHA-256 архива — `e41e94cf96ddf7f8fd614cccf2b69c97e10f42abfebf3378986592d325da1ca0`; он совпал с `SHA256SUMS` этого репозитория. У извлечённого `tokens.txt` SHA-256 совпал с установленной int8-моделью Reever.

Архив FP32 нужно распаковать прямо в `data/v3-fp32/`: `encoder.onnx` и внешний файл `encoder.weights` должны лежать рядом. Скрипт проверяет внешние файлы весов, перечисленные в `encoder.onnx`. Требуется Python 3.12 с `onnxruntime==1.28.0`, `onnx==1.19.1`, `onnx-ir`, `sherpa-onnx==1.13.8`, `numpy`, `soundfile` и `psutil`. В существующем `tools/kws/.venv` для этого эксперимента были дополнительно установлены `onnx==1.19.1` и `onnx-ir`.

```powershell
$py = 'tools/kws/.venv/Scripts/python.exe'
& $py tools/asr_quant/quantize_v3.py quantize b32
& $py tools/asr_quant/quantize_v3.py quantize b128
& $py tools/asr_quant/quantize_v3.py quantize b32-a4
& $py tools/asr_quant/quantize_v3.py benchmark tools/asr_quant/data/v3-int4-b128
```

Каждое квантование запускается отдельным процессом. Результаты находятся в `data/v3-int4-b32/`, `data/v3-int4-b128/` и `data/v3-int4-b32-a4/`. В каждой папке лежат `encoder.int8.onnx` и неизменённые копии `decoder.int8.onnx`, `joiner.int8.onnx`, `tokens.txt` из установленной int8-модели. Имя энкодера соответствует существующему поиску файлов в Reever. Все большие файлы остаются в игнорируемой папке `data/`.

## Результаты

Замеры 2026-10-21: Python sherpa-onnx 1.13.8, ONNX Runtime 1.28.0, CPU, четыре потока, `testdata/corpus/000_continuous.wav`. Каждая строка измерена в новом процессе. Память — прирост private bytes при создании `OfflineRecognizer`; время фразы — медиана четырёх прогретых распознаваний. Размеры указаны в десятичных МБ.

| Энкодер | Энкодер, МБ | Вся модель, МБ | Загрузка, с | Private, МБ | Фраза, мс | Текст |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| Исходный int8 | 652,2 | 670,5 | 1,65 | 718,1 | 136 | Ривер фотошоп |
| int4 b32 symmetric | 679,5 | 697,8 | 1,51 | 737,0 | 176 | Ривер фотошоп |
| int4 b128 symmetric | 629,5 | 647,8 | 1,42 | 686,5 | 173 | Ривер фотошоп. |
| int4 b32 symmetric, accuracy 4 | 679,5 | 697,8 | 1,86 | 911,4 | 115 | Ривер фотошоп. |

Все три int4-модели загрузились и распознали фразу. Квантователь заменил 217 `MatMul` с постоянными весами на `com.microsoft::MatMulNBits`; ещё 72 `MatMul` работают с динамическими весами. FP32-экспорт содержит около 304 МБ весов `Conv`, которые в этом эксперименте остаются FP32. В исходном int8-энкодере есть 77 узлов `ConvInteger` и 217 `MatMulInteger`. Поэтому квантование только `MatMul` до int4 не сократило память вдвое относительно уже квантованной int8-модели. Вариант b128 сэкономил около 31,5 МБ private bytes (4,4%), но распознавал эту фразу примерно на 37 мс дольше. Вариант b32 с accuracy 4 распознавал быстрее, но требовал намного больше памяти.

## Гибрид int4 MatMul + int8 Conv

Разбор `v3-int4-b128/encoder.int8.onnx` показал распределение данных ниже. Размеры учитывают каждый initializer один раз. В последней строке — отдельный тензор внутри узла `Constant`, поэтому он не входит в сумму initializers.

| Данные | Тип | МБ |
| --- | --- | ---: |
| Веса `MatMulNBits` | UINT8, упакованные 4 бита | 266,3 |
| Масштабы `MatMulNBits` | FP32 | 16,6 |
| Веса `Conv` | FP32 | 303,5 |
| `LayerNormalization`, `Add`, прочее | FP32 | 1,2 |
| Веса `MatMul` / `Gemm` | — | 0 |
| Таблица позиционного кодирования `Constant → Slice` | FP32, вне initializers | 41,0 |

Все 217 `MatMul` с постоянным вторым входом уже переведены в `MatMulNBits`. Оставшиеся 72 `MatMul` умножают активации самовнимания: их второй вход получается из `Reshape → Transpose`, а не из весового тензора. Узлов `Gemm` нет. Следовательно, сворачивать `Transpose` у весов здесь нечего.

Команда `hybrid` запускает `quantize_dynamic` только для `Conv` поверх существующего int4-энкодера. В результате 77 узлов становятся `ConvInteger`, а 303,5 МБ FP32-весов заменяются 75,9 МБ 8-битных весов. Передаётся `per_channel=True`, но ONNX Runtime 1.28.0 создаёт для каждого `Conv` скалярный масштаб: все 77 весов квантуются по тензору. Параметр `--unsigned` выбирает UINT8-веса, как в исходной int8-модели; без него используются INT8-веса.

Команда `pos16` хранит фиксированную таблицу позиционного кодирования `[1, 9999, 1024]` в FP16 вместо FP32 (20,5 вместо 41,0 МБ). После динамического `Slice` использованный фрагмент приводится к FP32, чтобы типы последующих узлов не изменились. Быстрый прогон FLEURS показал расхождения в точности, поэтому этот вариант оставлен только для сравнения.

Команда `pos4096` сохраняет FP32-значения точно: берёт центральные 4096 позиций и меняет центр индексации с 5000 на 2048 в двух константах. Для длины выхода энкодера `T ≤ 2048` срез таблицы совпадает с исходным побайтно. Проверка ONNX Runtime на входах примерно 2 и 24 секунды дала полностью одинаковые выходы энкодера; самый длинный клип выбранной выборки FLEURS длится 33 секунды, а Reever ограничивает сегменты 24 секундами (`COMMAND_LIMITS` и `DICTATION_LIMITS` в `engine.rs`). `pos2048` делает то же для 2048 позиций (`T ≤ 1024`). Для более длинного аудио, при выходе за соответствующий предел `T`, нужен вариант с полной таблицей.

```powershell
& $py tools/asr_quant/quantize_v3.py quantize b256
& $py tools/asr_quant/quantize_v3.py hybrid b128 --unsigned
& $py tools/asr_quant/quantize_v3.py pos16 b128 --unsigned
& $py tools/asr_quant/quantize_v3.py pos4096 b128 --unsigned
& $py tools/asr_quant/quantize_v3.py benchmark tools/asr_quant/data/v3-hybrid-b128-conv8u-pos4096
```

## Быстрая проверка FLEURS

Для каждого сравнения использованы одинаковые 30 записей dev на языке (`ru_ru`, `en_us`, `de_de`), seed 42. WER нормализован приведением к нижнему регистру, удалением пунктуации и заменой ё→е. В таблице показаны проценты WER и средняя разница с int8 в процентных пунктах; полные отчёты лежат в игнорируемых `data/fleurs-hybrid-*.md`.

| Вариант | ru_ru | en_us | de_de | ΔWER, среднее |
| --- | ---: | ---: | ---: | ---: |
| int8 | 12,13 | 9,12 | 7,80 | 0,00 |
| b128-conv8pc-pos4096 | 12,13 | 9,61 | 8,29 | +0,33 |
| b128-conv8u-pos4096 | 12,13 | 9,45 | 8,29 | +0,27 |
| b256-conv8u-pos4096 | 12,92 | 9,93 | 7,48 | +0,42 |
| b128-asym-conv8u-pos4096 | 13,11 | 9,61 | 8,29 | +0,65 |
| b64-conv8u-pos2048 | 12,13 | 9,12 | 9,11 | +0,43 |
| b128-conv8u-pos16 | 12,52 | 9,77 | 8,13 | +0,46 |
| b256-conv8u-pos16 | 12,52 | 10,42 | 6,99 | +0,29 |

**Рекомендация для дальнейшего эксперимента:** `v3-hybrid-b128-conv8u-pos4096`. Относительно исходного int8 энкодер уменьшился с 652,2 до 378,1 МБ, прирост private bytes при загрузке — с 718,8 до 440,1 МБ. На этом коротком файле время распознавания выросло со 125 до 185 мс. На 90 записях FLEURS средний WER вырос на 0,27 п.п.; это близкий результат, но полного равенства точности тест не подтвердил. Для длинного аудио с выходом энкодера `T > 2048` используйте вариант с полной таблицей. В приложение ничего не внесено.
